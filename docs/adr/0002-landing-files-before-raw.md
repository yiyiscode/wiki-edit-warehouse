# ADR 0002:API 回應先落地成檔案,再載入 raw

- 狀態:已採納
- 日期:2026-11-12
- 決策者:使用者;AI 提案並提供替代方案

## 背景

- 來源只保留 30 天(SPEC 第 5 節,實測 2026-11-11)。回補每晚開始一小時,最早那一小時的資料就永久取不回。
- raw 冪等載入(`load_raw`)屬於使用者手寫清單(SPEC 第 11 節),寫完需要時間。
- SPEC v0.2 原設計是 API → raw 表,中間沒有檔案;照原設計,回補要等 `load_raw` 寫完才能開始。

## 決定

擷取與載入拆成兩步,中間以檔案交接:

1. `python -m ingest.backfill fetch`:API → `data/landing/<wiki>/<YYYY-MM-DDTHH>.jsonl.gz`,一個小時一個檔,內容是 API 回傳的紀錄,一行一筆、不做修改。
2. `python -m ingest.backfill load`:落地檔 → `raw.raw_recentchange`,經由 `load_raw`。

規則(對應 `src/ingest/backfill.py`):

- 檔案存在即代表該小時已抓完;先寫暫存檔、寫完才改名,中斷不會留下半個檔。
- 只抓已結束的小時;抓到 0 筆不落檔,下次重試。
- 落地檔不進版控(`.gitignore` 的 `data/`),與 raw 一樣永不刪除。

## 理由

- 擷取不必等手寫的載入完成,先把快過期的資料救下來。
- raw 表可以從落地檔重建;落地檔成為第二份副本,不必只靠 `pg_dump`。
- 重複載入同一批檔案正好是 `load_raw` 冪等性的實地驗證。

## 代價

- 多一層要說明與維護;SPEC 原本「raw 是唯一副本」的說法改為「落地檔與 raw 是僅有的兩份副本」。
- 落地檔與 raw 表在同一台筆電,硬碟損壞時兩份一起消失;異地備份不在本決定範圍內。
- 落地檔是否「完整」只靠「檔案存在」判斷,沒有逐檔的筆數或雜湊紀錄。

## 替代方案

| 方案 | 取捨 |
|---|---|
| 只當 M1 的臨時措施,M4 起 Airflow 直接 API → raw | SPEC 幾乎不用改;少一份副本,raw 表損壞時只能靠每週的 `pg_dump` |
| 不落地,照 SPEC 直接 API → raw | 架構最簡單;回補要等 `load_raw` 寫完,等待期間最舊的資料持續過期 |
